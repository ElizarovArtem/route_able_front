# Frontend Architecture

This project uses a feature-sliced structure with explicit layer prefixes. The prefixes keep folders sorted and make dependency direction visible.

## Layers

### `a.app`

Application wiring:

- React entrypoint in `src/a.app/entrypoint/main.tsx`
- generated TanStack route tree in `src/a.app/entrypoint/routeTree.gen.ts`
- file-based routes in `src/a.app/routes`
- root providers and app layout
- global Zustand store composition
- global SCSS and variables

Keep this layer focused on setup and composition. Do not put reusable business logic here.

### `b.pages`

Route-level page compositions. Pages assemble widgets, features, entities, and shared UI into screens.

Pages should stay thin. If logic becomes reusable or action-oriented, move it to `d.features`; if it describes a domain object, move it to `e.entities`.

### `c.widgets`

Large reusable UI blocks used by pages. Widgets compose entities, features, and shared UI into meaningful page sections such as chats, meal blocks, calendars, lesson sections, and AI assistant panels.

Widgets should not own low-level domain request functions or global stores. Put those into the relevant entity or feature slice.

### `d.features`

User actions and business flows. A feature answers "what can the user do?"

Common examples:

- auth and user updates
- booking or cancelling lessons
- creating meal/workout plans
- creating payments or subscriptions
- sending messages
- starting or completing AI workout actions

Typical structure:

```text
src/d.features/<segment>/
  api/
    queries/
    requests/
  model/
  ui/
  index.ts
```

Use `api/queries` for React Query hooks and `api/requests` for plain API calls. Use `model` for stores, resolvers, schemas, constants, and helper logic owned by the feature.

### `e.entities`

Domain objects and their basic behavior. An entity answers "what is this?"

Current segments include users, lessons, meals, workouts, subscriptions, coach billing, feedback, reviews, AI assistant, and day data.

Typical structure:

```text
src/e.entities/<segment>/
  api/
    queries/
    requests/
  model/
  ui/
  index.ts
```

Entity APIs should primarily read or describe domain data. Mutations that represent a user action usually belong in `d.features`.

### `f.shared`

Cross-cutting infrastructure:

- `api`: Axios client, interceptors, Socket.IO connection
- `config`: environment access
- `lib`: generic helpers and hooks
- `ui`: local UI primitives and icons

Shared code must not depend on app, pages, widgets, features, or entities.

## Dependency Direction

Imports should flow downward:

```text
a.app -> b.pages -> c.widgets -> d.features -> e.entities -> f.shared
```

Rules:

- `f.shared` imports only from `f.shared` or external packages.
- `e.entities` can import from `f.shared`.
- `d.features` can import from `e.entities` and `f.shared`.
- `c.widgets` can import from `d.features`, `e.entities`, and `f.shared`.
- `b.pages` can import from widgets, features, entities, and shared.
- `a.app` can compose all layers.

Avoid importing upward or sideways between unrelated slices. If two slices need the same helper, move the helper down to a shared or entity-level location that both can depend on.

## Public Exports

Prefer importing from a slice `index.ts` when it exposes the needed API. Deep imports are acceptable when the existing slice already uses them or when a module is intentionally not part of the public slice interface.

When adding new reusable exports, update the nearest `index.ts` rather than making consumers reach into implementation folders.

## Routing

Routes live in `src/a.app/routes`. Keep route files focused on routing and page selection. Put screen layout into `b.pages` and reusable page blocks into `c.widgets`.

Do not manually edit `src/a.app/entrypoint/routeTree.gen.ts`; it is generated by TanStack Router tooling.

## State And Data

Use TanStack Query for server state. Query hooks should live in the owning `api/queries` folder and call request functions from `api/requests`.

Use Zustand for global client state only when state must be shared across screens or app-wide flows. Compose typed slices in `src/a.app/store/store.ts`.

Prefer local React state for temporary UI state such as modal visibility, active tabs, and form-only state unless existing patterns in the slice use a store.

## Styling

Use SCSS modules beside components. Global styles and variables belong in `src/a.app/styles`.

Prefer local shared UI primitives from `src/f.shared/ui` for app-specific controls. Use Ant Design when it already appears in the feature or when it provides complex behavior that would be wasteful to rebuild.

## Adding A New Feature

1. Identify the owning domain segment.
2. Put read/query domain data in `e.entities/<segment>`.
3. Put user actions and mutations in `d.features/<segment>`.
4. Compose larger reusable screen blocks in `c.widgets`.
5. Compose final screens in `b.pages`.
6. Wire the route in `src/a.app/routes`.
7. Export intended public APIs through each slice `index.ts`.
8. Add focused tests for resolvers, hooks, forms, or UI behavior touched by the change.
